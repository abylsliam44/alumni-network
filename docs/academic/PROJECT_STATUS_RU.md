# Alumni Network: что реализовано и как это соответствует Assignment #6

**Состояние на 7 ноября 2026 года.**  
**Задание:** Assignment #6 — Designing the data layer and backend for a NoSQL recommendation platform.  
**Тема:** NoSQL-Based Project Recommendation Platform for Students and Alumni.  
**Исходный репозиторий:** <https://github.com/abylsliam44/alumni-network>  
**Рабочая ветка:** `feature/academic-nosql`.

## 1. Итог и оговорка о готовности

Создана и локально запущена учебная версия Alumni Network. Студенты и выпускники могут просматривать проекты, редактировать профиль, получать рекомендации, сохранять проекты и отправлять отклики. Учебный backend использует MongoDB для пользователей, проектов, откликов и взаимодействий. Для демонстрации подготовлены синтетические данные и отдельное Docker Compose-окружение.

**Работа ещё не прошла полную приёмку по ТЗ.** Ниже различаются три ситуации:

- **Реализовано и частично проверено** — код есть, проведена указанная проверка, но она может не покрывать требование целиком.
- **Реализовано, требует проверки** — соответствующая логика есть в коде, однако приёмочный сценарий полностью не выполнен.
- **Не завершено** — работа, проверка или доказательства ещё отсутствуют.

Особенно важно не считать прохождение трёх интеграционных тестов доказательством прохождения всех AC-01–16. Документы [API](API.md), [модели данных](DATA_MODEL.md) и [итогового отчёта](REPORT.md) пока являются черновиками.

Пользователь подтвердил, что альтернативная тема согласована с преподавателем. В проекте нет независимого документального подтверждения этого согласования. Прямая связь рекомендательной системы с темой диссертации по ASR не заявляется; раздел *Relevance to the dissertation* подготовлен в [proposal](PROPOSAL.md).

## 2. Предметная область и сценарий работы

Система связывает три основные сущности:

1. **Пользователи:** студенты и выпускники со своими навыками, интересами и предпочтениями по категориям проектов.
2. **Проекты:** идеи и проекты сообщества с описанием, категорией, стадией, требуемыми ролями и навыками.
3. **Взаимодействия:** просмотр, сохранение, отмена сохранения, оценка и отклик на проект.

Гость может просматривать каталог и карточки проектов, зарегистрироваться или войти. Авторизованный пользователь может заполнить профиль, найти проект, получить рекомендации и откликнуться. Автор проекта и администратор имеют доступ к управлению проектом и списку откликов. Администратор создаётся через демонстрационный seed, а не через публичную регистрацию.

## 3. Что сделано

### 3.1. Архитектура и локальная инфраструктура

- Добавлен выбор учебного режима через `ACADEMIC_NOSQL_MODE=true` до импорта приложения обычного режима. Для интерфейса используется `VITE_ACADEMIC_NOSQL_MODE=true`.
- Учебный поток работает по схеме **React → FastAPI → MongoDB**. Основные учебные данные не записываются через SQLAlchemy в PostgreSQL.
- Добавлен [отдельный Compose-файл](../../docker-compose.academic.yml): MongoDB 7 в режиме одноузлового replica set, backend и frontend. Отдельный volume хранит учебные данные.
- Локальные адреса: frontend — `http://localhost:3031`, API — `http://localhost:8011`, Swagger — `http://localhost:8011/docs`. В момент подготовки отчёта frontend и Swagger вернули HTTP 200, а `/api/health/ready` вернул `ready`.
- Отдельный образ учебного backend не требует запуска PostgreSQL, Redis, Qdrant, MinIO, Celery или внешнего AI API. Есть origin guard, liveness и readiness с проверкой MongoDB replica set.
- Production Compose и его volumes не менялись. Проверка полной совместимости исходного режима после изменений ещё не проведена.

Реализация учебного backend сейчас сосредоточена преимущественно в [academic/main.py](../../backend/app/academic/main.py) и [academic/db.py](../../backend/app/academic/db.py). Это не полностью повторяет предложенное в ТЗ разделение на router, repositories и services; при дальнейшем развитии необходим рефакторинг и проверка границ модулей.

### 3.2. Модель MongoDB

| Коллекция | Что хранится | Почему так |
| --- | --- | --- |
| `users` | Пользователь, внутренние данные авторизации и вложенный профиль | Профиль принадлежит одному пользователю и обычно читается вместе с ним. |
| `projects` | Содержимое проекта, автор, нормализованные навыки и теги, даты, soft delete | Проект является самостоятельной сущностью каталога. |
| `project_applications` | Отклики с ссылками на проект и пользователя | Количество откликов не ограничено и не должно увеличивать документ проекта. |
| `interactions` | События VIEW, SAVE, UNSAVE, RATE и APPLY | История растёт независимо и не встраивается в профиль. |

Документы используют строковые UUID, даты MongoDB и `schema_version`. Навыки и теги нормализуются для сравнения; email нормализуется для проверки уникальности. Добавлены MongoDB validators для основных полей и enum и индексы для email, каталога, навыков, откликов и истории. Уникальный составной индекс ограничивает пару «проект — заявитель». Валидаторы реализованы для основных полей, но их полное соответствие всем ограничениям ТЗ ещё нужно проверить.

Модель, индексы и компромиссы описаны в [DATA_MODEL.md](DATA_MODEL.md). MongoDB не создаёт внешние ключи между коллекциями: связанные сущности проверяются прикладной логикой и импортом.

### 3.3. Авторизация, проекты и взаимодействия

- Добавлены регистрация STUDENT/ALUMNI, вход, refresh, logout и получение текущего пользователя. Для паролей используется bcrypt, для сессий — JWT в HttpOnly cookies. Приватные поля не включаются в публичную функцию формирования пользователя.
- Добавлены профиль, каталог пользователей, создание, просмотр, частичное обновление и soft delete проектов. Изменение и удаление проверяют владельца либо администратора; запись также ограничивается условием владельца.
- При отклике application и событие APPLY записываются в одной MongoDB-транзакции. Уникальный индекс защищает от повторного отклика. Событие APPLY нельзя передать через публичную схему взаимодействий.
- Добавлены VIEW, SAVE, UNSAVE и RATE, собственная история и список сохранённых проектов. `event_id` используется как ключ идемпотентности: идентичный повтор возвращает 200, конфликт содержимого — 409.
- Добавлены маршруты авторизации, профилей, каталога, проектов, откликов, кандидатов и взаимодействий. Их перечень находится в [API.md](API.md); полноту схем ответов и совпадение Swagger с контрактом ТЗ ещё нужно проверить.

Атрибуты cookies и настройки учебного origin guard в текущей реализации заданы для локального режима; их полное соответствие настраиваемому поведению обычного приложения не подтверждено. Учебный режим не следует считать production-конфигурацией.

### 3.4. Поиск и рекомендации

Каталог поддерживает MongoDB text search и фильтры проекта; предусмотрены сортировки `latest`, `match`, `popular` и пагинация. Text search работает по словам с `default_language: none`: поиск подстрок, исправление опечаток и семантическое сходство не обещаются.

Работающий content-based baseline рассчитывает:

```text
балл = round(100 × (0,70 × покрытие навыков
                  + 0,20 × совпадение категории
                  + 0,10 × совпадение интересов и тегов))
```

Для пустого знаменателя соответствующий компонент равен нулю. Ранжирование выполняется в MongoDB aggregation до пагинации. Персональная выдача исключает удалённые проекты, собственные проекты пользователя и проекты, на которые уже отправлен отклик. При отсутствии сигналов используется порядок по дате и идентификатору. Автор и количество откликов для выбранной страницы загружаются пакетно. Результат показывается как **баллы соответствия**, а не как вероятность успеха.

В seed предусмотрен старый проект с лучшим совпадением: при ручной проверке он занял первое место, несмотря на то что новее него было более 100 проектов. Это демонстрирует конкретный сценарий глобального ранжирования, но не заменяет полный набор автоматических тестов алгоритма. Гибридная модель и метрики Precision@K, Recall@K и NDCG@K описаны как план для Final Project, не как доказанная эффективность текущей системы.

### 3.5. Интерфейс

Учебный интерфейс переработан в визуальном языке существующей платформы: тёмная тема, боковая навигация, типографика и акценты Alumni Network. Обновлены каталог и фильтры, карточки и страница проекта, рекомендации, сохранённые проекты, сообщество, история, профиль, вход, регистрация и форма проекта. Добавлены состояния загрузки, пустой выдачи и ошибок, а также адаптивные стили для узких экранов.

В Safari вручную проверены вход, каталог, рекомендации, переход в карточку проекта, сохранение/отмена сохранения и поиск с пустой выдачей и сбросом. Полная проверка мобильных устройств, всех форм и прямых переходов на отключённые страницы не проводилась. Пример текущего интерфейса: [скриншот рекомендаций](screenshots/recommendations.png).

### 3.6. Данные и импорт

- [academic_seed.py](../../backend/scripts/academic_seed.py) создаёт воспроизводимые синтетические данные: **50 пользователей, 120 проектов, 50 откликов и 550 событий**. Сюда входит один локальный администратор. `--reset` ограничен базой `alumni_academic` и удаляет данные учебных коллекций.
- Локальные демонстрационные данные и учётная запись описаны в [SETUP.md](SETUP.md); они предназначены только для демонстрации.
- Добавлен [offline-импорт из PostgreSQL](../../backend/scripts/academic_import_from_postgres.py). Dry run используется по умолчанию; чтение источника открывается как `read-only`, `repeatable read`. При импорте сохраняются UUID и hashes, нормализуются данные, проверяются роли, ссылки и конфликты, для application детерминированно создаётся APPLY.
- На небольшом синтетическом источнике dry run не записал пользователей в MongoDB. Два импорта подряд оставили 2 users, 1 project, 1 application и 1 APPLY без дублей. Конфликт при изменении импортированного документа был выявлен в отдельной проверке. Все возможные неоднородные данные старой базы и все варианты конфликтов ещё не проверены; импорт не следует запускать на production-данных.

## 6. Результаты проверок и производительность

Подтверждено в ходе работы:

- Docker Compose прошёл проверку конфигурации; учебные сервисы запущены.
- Выполнены три интеграционных теста на отдельной базе MongoDB replica set: конкурентный отклик, запрет изменения чужого проекта и идемпотентность interaction.
- Frontend production build завершился успешно; отдельный ESLint для `src/Academic.jsx` прошёл.
- Общий `npm run lint` завершался с семью ошибками в существующих страницах вне учебного компонента. Общий lint всего проекта поэтому нельзя считать пройденным.
- Проведена минимальная синтетическая проверка offline-импорта. Полной проверки всех вариантов исходных данных нет.

На отдельной benchmark-базе с 10 000 проектов, 1 000 пользователей и 100 000 событий выполнены по 10 прогревочных и 100 измеряемых последовательных запросов. Стенд: Apple M1 Pro, 32 ГБ RAM, MongoDB 7.0.45, Docker 29.1.3. После вторичных индексов p95 составил:

| Запрос | p95 после индексов |
| --- | ---: |
| Каталог | 0,35 мс |
| Фильтр категории | 0,34 мс |
| Фильтр навыков | 0,40 мс |
| История | 0,32 мс |
| Расчёт baseline рекомендаций | 26,62 мс |

Это замеры **запросов драйвера MongoDB внутри контейнера**, без полного HTTP-цикла, обогащения связанными данными и интерфейса. Поэтому по ним нельзя утверждать выполнение целевых p95 для пользовательского API. Агрегация рекомендаций просмотрела все 10 000 документов; вычисляемый score не стал индексным. Полная таблица до/после и `executionStats`: [VALIDATION.md](VALIDATION.md), [benchmark.json](benchmark.json).

## 7. Что необходимо закончить перед сдачей

3. Расширить проверку импорта на неоднородные реальные структуры в изолированной тестовой среде; не использовать production-данные без отдельного безопасного процесса.
4. Провести полный HTTP benchmark и зафиксировать результаты отдельно от текущих замеров драйвера. Устранить или отдельно обосновать существующие ошибки общего frontend lint; выполнить оставшиеся backend-проверки.
5. Подготовить недостающие скриншоты регистрации/профиля, коллекций и индексов, каталога и поиска, отклика и истории, Swagger и explain. Исключить из изображений пароли, cookies и токены.
6. Завершить [REPORT.md](REPORT.md), дополнить примеры API и описание модели, сверить формат с требованиями курса и приложить подтверждение согласования темы, если оно требуется.

## 8. Как запустить и где смотреть исходники

Полные команды, ограничения импорта и порядок остановки находятся в [SETUP.md](SETUP.md). Краткий запуск:

```bash
cp .env.academic.example .env.academic
docker compose --env-file .env.academic -f docker-compose.academic.yml up -d --build
docker compose --env-file .env.academic -f docker-compose.academic.yml exec backend python scripts/academic_create_indexes.py
docker compose --env-file .env.academic -f docker-compose.academic.yml exec backend python scripts/academic_seed.py --seed 42
```

Повторное копирование примера поверх уже настроенного `.env.academic` может затереть локальные настройки; если файл существует, использовать его и не перезаписывать. Синтетический демонстрационный вход указан в [SETUP.md](SETUP.md).

Ключевые файлы: [ТЗ](../../alumni_nosql_implementation_spec.md), [учебный backend](../../backend/app/academic/main.py), [модель/индексы MongoDB](../../backend/app/academic/db.py), [учебный frontend](../../frontend/src/Academic.jsx), [стили интерфейса](../../frontend/src/academic.css), [исходные результаты проверки](VALIDATION.md).
