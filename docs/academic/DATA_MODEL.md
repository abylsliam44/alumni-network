# Academic MongoDB data model — draft

`users` embeds the bounded profile: public professional fields, skills, normalized skills, interests and category preferences. Email and password hash remain internal. `projects` references its creator by UUID and contains normalized skill/tag arrays, timestamps and a soft-delete marker. `project_applications` references a project and applicant; a unique compound index prevents duplicate applications. `interactions` references the user and project, and stores VIEW, SAVE, UNSAVE, RATE or backend-generated APPLY with its event UUID. A user's history is never embedded in their profile.

Dates are UTC BSON dates, IDs are canonical UUID strings and documents carry `schema_version: 1`. Collection validators check core field types and enums. The script `academic_create_indexes.py` creates indexes for normalized email, user filters and skills, project date/category/roles/skills/text search, application uniqueness and history/state queries. Text search uses language `none`; it is word search, not substring or typo correction. MongoDB does not enforce cross-collection foreign keys; the service must check references.

Document embedding makes the profile a convenient atomic unit but creates document size and duplication trade-offs. Referencing keeps unbounded event history separate, at the cost of joins and explicit consistency checks. Key-value storage is simple for direct lookup but less suited to filtering and aggregation; graph databases offer native traversal but would introduce another data system for this scope. Compared with PostgreSQL, MongoDB offers flexible documents and multikey indexes but requires explicit reference checks and transactions for cross-document invariants. A single-node replica set is intended only for local transaction demonstrations.

Driver-level `explain` and synthetic benchmark measurements are recorded in [VALIDATION.md](VALIDATION.md); end-to-end HTTP performance still needs verification.
