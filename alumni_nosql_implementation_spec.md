## 3. Границы реализации и архитектурное решение

### 3.1. Учебный режим

Добавить переключатель `ACADEMIC_NOSQL_MODE=true`. В этом режиме MongoDB является единственным основным хранилищем для авторизации, профилей, каталога проектов, откликов и истории взаимодействий. PostgreSQL для этих операций не используется. Изменение одного `DATABASE_URL` не является реализацией миграции: SQLAlchemy-запросы необходимо заменить MongoDB-репозиториями.

При `ACADEMIC_NOSQL_MODE=false` существующий режим приложения продолжает работать без изменения контрактов. Режим выбирается при старте процесса; переключение во время работы не поддерживается. Автоматического резервного перехода с MongoDB на PostgreSQL нет.

В учебном режиме подключаются только маршруты auth, profile, directory, projects, interactions и health. Не подключать SQL-зависимые startup handlers, WebSocket, фоновые задачи и прогрев рекомендаций людей. Выбор режима должен происходить до инициализации соответствующих клиентов и маршрутов; одного скрытия UI недостаточно.

Во frontend добавить `VITE_ACADEMIC_NOSQL_MODE=true`. В учебном режиме оставить вход, регистрацию, профиль, каталог пользователей, проекты, рекомендации проектов и историю. Убрать переходы в чаты, вакансии, мероприятия, резюме, AI-chat, рекомендации людей, менторство и видеозвонки. После входа открывать каталог проектов. Прямые переходы на отключённые страницы показывают страницу «Недоступно в учебном режиме».

### 3.2. Состав

- React → FastAPI → MongoDB.
- Отдельный `docker-compose.academic.yml`: MongoDB, backend, frontend.
- MongoDB — replica set из одного узла для локальных транзакций между коллекциями; startup должен дождаться его инициализации.
- Нормальный production compose и его volumes не изменять.
- Учебная демонстрация не требует PostgreSQL, Redis, Qdrant, MinIO, Celery и внешних AI API.
- Учебный профиль хранит текстовые поля; загрузку аватаров, обложек и резюме в этом режиме отключить. Допускается необязательный `photo_url` с внешней ссылкой.

Новые модули разместить в `backend/app/academic/`: `router.py`, `deps.py`, `schemas.py`, `repositories/`, `services/`. Подключение и lifecycle MongoDB — `backend/app/core/mongodb.py`. Общие enum предметной области вынести из SQLAlchemy-моделей в нейтральный модуль, например `backend/app/domain/project_enums.py`, с сохранением старых импортов через реэкспорт. Учебные схемы и auth dependency не должны зависеть от SQLAlchemy-сессии или ORM User.

## 5. Модель MongoDB

База: `alumni_academic`. Обязательные коллекции: `users`, `projects`, `project_applications`, `interactions`. Не встраивать неограниченную историю и отклики в документ пользователя или проекта.

### 5.1. Общие правила

- `_id` — каноническая строка UUID; публичное поле `id` формируется из `_id`.
- Все ссылки между документами — строки UUID того же формата. Существующие UUID при переносе сохраняются.
- Даты — BSON Date в UTC; API возвращает ISO 8601 с часовым поясом.
- Enum сохраняются строками с текущими значениями из репозитория.
- `schema_version: 1` у каждого документа.
- Вход проверяется Pydantic; обязательные типы и enum дополнительно фиксируются MongoDB validators.
- Навыки и теги: удалить лишние пробелы, пустые элементы и повторы без учёта регистра; для сравнения хранить нормализованные ключи `skills_normalized`, `required_skills_normalized`, `tags_normalized`.
- MongoDB не обеспечивает внешние ключи: существование связанных сущностей проверяет сервис; массовый импорт выполняет отдельную проверку ссылочной целостности.

### 5.2. `users`

Поля: `_id`, `email`, `email_normalized`, `hashed_password`, `name`, `role`, `is_active`, `is_admin`, `photo_url`, `bio`, `created_at`, `updated_at`, `schema_version`.

Вложенный `profile`: `headline`, `skills`, `skills_normalized`, `career_interests` (массив строк), `preferred_project_categories` (массив ProjectCategory), `education`, `experience`, `location`, `graduation_year`, `linkedin_url`, `github_url`, `website_url`.

Ограничения: имя 1–100 символов; bio до 5000; skills до 100 элементов, каждый до 80 символов; категории без повторов. Email обрезается по краям и приводится к нижнему регистру для проверки уникальности. В публичном профиле выдавать только имя, bio, роль, photo_url и перечисленные профессиональные поля; email не выдавать.

Встраивание профиля обосновано тем, что он принадлежит одному пользователю и читается вместе с ним. Password hash доступен только внутреннему auth repository и не сериализуется наружу.

### 5.3. `projects`

Сохранить поля существующего ProjectBase: `title`, `short_description`, `full_description`, `category`, `required_roles`, `required_skills`, `project_stage`, `team_size`, `is_remote`, `contact_preference`, `github_link`, `demo_link`, `tags`, `university_related`, `startup_idea`, `looking_for_cofounder`.

Дополнить: `_id`, `created_by_user_id`, `required_skills_normalized`, `tags_normalized`, `created_at`, `updated_at`, `deleted_at` (null для активных), `schema_version`.

Сохранить текущие enum ProjectCategory, ProjectRole и ProjectStage. Сохранить текущие ограничения длины title и short_description; ограничить full_description 20 000 символами, skills/tags 100 элементами. Обязательные поля нельзя обнулить через update. `PUT` сохраняет существующую семантику частичного обновления по переданным полям; зафиксировать это в OpenAPI.

В ответах вычислять `creator`, `applications_count`, `has_applied`, `matched_skills`, `match_score`; не хранить их как обязательные дублирующие поля документа.

### 5.4. `project_applications`

Поля: `_id`, `project_id`, `applicant_id`, `message`, `skills`, `fit_reason`, `status`, `applied_at`, `schema_version`. Сохранить текущие ProjectApplicationStatus и ограничения DTO. Новая заявка получает SUBMITTED.

Один пользователь может отправить один отклик на проект. Отклик на собственный или удалённый проект запрещён. Уникальность обеспечивает составной индекс, а не только предварительный SELECT/find. Создание отклика и события APPLY выполняется в одной MongoDB-транзакции.

### 5.5. `interactions`

Поля: `_id`, `user_id`, `item_id` (UUID проекта), `item_type: "PROJECT"`, `event_type`, `created_at`, `rating` (только RATE), `schema_version`. `_id` служит идентификатором идемпотентности события.

| Событие | Источник | Семантика |
|---|---|---|
| VIEW | Клиент после успешного открытия карточки | Просмотр авторизованным пользователем |
| SAVE | Кнопка «Сохранить» | Добавить проект в сохранённые |
| UNSAVE | Кнопка отмены сохранения | Отменить сохранение |
| RATE | Оценка пользователем | Целое число 1–5 |
| APPLY | Только backend отклика | Успешная подача заявки |

SAVE/UNSAVE и RATE хранятся как события; текущее состояние определяется последним событием по `(created_at, _id)`. VIEW/APPLY не отменяют SAVE. Повторный запрос с тем же `_id` и тем же содержимым не создаёт запись; с другим содержимым возвращает 409. `user_id` и время выставляет сервер. APPLY через публичный endpoint взаимодействий запрещён. Историю не удалять автоматически по TTL.

## 8. Удаление, целостность и конкурентные операции

- DELETE проекта — soft delete: установить deleted_at, ответ 204. В обычном каталоге, рекомендациях, сохранённых и новых откликах удалённый проект недоступен.
- Исторические отклики и события сохраняются; история может показывать item_id и отметку «Проект удалён».
- Изменение и удаление проверяют владельца в условии записи, а не только отдельным предварительным чтением.
- Создание отклика выполняется транзакционно: условная запись в активный документ проекта (например, инкремент внутреннего `application_write_version`), вставка application, вставка APPLY. Это сериализует конфликт с удалением. Уникальный индекс пары окончательно защищает от дублей; транзакционные transient errors повторяются ограниченное число раз.
- POST interactions также проверяет активность проекта в транзакции с условным обновлением внутреннего `interaction_write_version`, затем записывает событие. Повтор уже существующего event_id возвращает прежний результат при совпадении данных, даже если проект позже удалён.
- До подтверждения commit API не отвечает успехом. Внутренние version-поля не выдаются наружу.
- Регистрация атомарна в одном users-документе; гонка email обрабатывается через unique constraint.

### 9.1. Обязательный baseline для Assignment #6

Использовать content-based ranking без внешнего LLM. Для пользователя u и проекта p:

```text
skill_score = |user.skills_normalized ∩ project.required_skills_normalized|
              / |project.required_skills_normalized|
category_score = 1, если category входит в preferred_project_categories; иначе 0
interest_score = |normalized(career_interests) ∩ project.tags_normalized|
                 / |project.tags_normalized|
score = round(100 × (0.70 × skill_score + 0.20 × category_score + 0.10 × interest_score))
```

При нулевом знаменателе соответствующий компонент равен 0. Все компоненты в [0,1]. Сравнение интересов с тегами — точное по нормализованным ключам; синонимы и семантическое сходство не заявляются.

Для `/projects/recommended` исключить собственные, удалённые проекты и проекты с уже отправленным откликом. `match_score` в ProjectRead — этот baseline, `matched_skills` — совпавшие исходные названия навыков. Дополнительно выдавать `recommendation_reason`: перечисление совпадений либо «Новый проект для знакомства» при нулевом score. Это балл ранжирования, не вероятность успеха.

Сортировка: score DESC, created_at DESC, _id ASC. Ограничение и пагинация применяются после расчёта и сортировки всех подходящих проектов. Не повторять ограничение текущего кода в 100 последних проектов. Расчёт score и сортировку выполнить в aggregation pipeline; связанные counts и creator загружать пакетно для выбранной страницы, исключив N+1.

`sort=match` в каталоге использует ту же формулу до пагинации, но не исключает собственные проекты и проекты с откликом. `sort=popular` ранжирует по количеству откликов, затем created_at и _id; count вычисляется по applications. Для гостя `sort=match` работает как latest с нулевым score.

Cold start: при отсутствии профильных сигналов все scores=0; выдавать подходящие проекты по дате и _id. Для `/candidates` использовать покрытие требований проекта навыками кандидата, 0–100, положительные scores; исключить автора и неактивных пользователей, ранжировать до limit. Не ограничивать подбор произвольными первыми 200 пользователями.

### 9.2. План для Final Project, не обязательная реализация сейчас
